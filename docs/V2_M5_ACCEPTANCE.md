## 工程交付

- [x] 从最新整份已确认报告中选择 1–3 项 P0 指标，保存原值、单位和报告日期；不根据数值自行诊断。
- [x] 先执行 A/B/C 安全门禁，再从当前有效、具名审核的食谱、食材、禁忌和来源中匹配目标标签。
- [x] 过滤缺失的发布版本、停用来源、演示审核和合成种子；任何约束下不足 3 道合格食谱时明确降级，不编造内容。
- [x] 支持份数、开始日期、时间、每份预算、厨具、口味、地域和不可得食材；仅使用已发布的替代材料及审核比例。
- [x] 生成 3–7 张完整食谱卡、每日一项的 7 天示例安排和按可食部克数合并的采购清单；结构化 `max_weekly_uses` 限制每道食谱的周频次。
- [x] `READY → ACTIVE → PAUSED` 快照；确认前重跑安全与内容校验，来源或风险变化后暂停活动方案；重复请求幂等。
- [x] 参与者专属方案接口、JSON 导出、前端核对页面、来源与版本追溯、最小化审计。

## 本地证据

- `tests/test_care_plan_service.py`：BMI、空腹血糖、甘油三酯三个**合成工程案例**；份数/采购量重算、替代、周频次、预算、草稿隔离、高风险门禁、来源撤回、API 授权与导出。
- 后端：`python -m pytest -q`。
- 前端：`npm run typecheck`、`npm run build`。
- 迁移：临时 SQLite 库完成 `upgrade head → downgrade -1 → upgrade head`。

测试使用的审核角色和来源均为自动化夹具，不证明真实专业审核，也不表示案例方案具有个体医学适用性。当前仓库的 20 道合成食谱仍为草稿，缺少经审核的目标标签及结构化每周使用上限，因此正式参与者路径会安全阻断。
