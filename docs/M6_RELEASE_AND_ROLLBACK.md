# M6 发布检查与回滚方案

准备日期：2026-10-04。当前不具备正式发布条件。

## 发布前核对

1. M4/M5 微信开发者工具、Android/iOS 真机、弱网、权限拒绝及存储异常证据齐全，未关闭 P0/P1 为零；依赖审计告警需逐项判断和处理。
2. 完成 3—5 人走查与 10—20 人封闭试用，核心任务完成率不低于 90%，实际结果写入 `M6_TRIAL_RESULTS.json`，`npm run check:m6` 通过。
3. 提供真实主体、AppID、隐私联系人、授权文件及正式签署版本；AppID 必须与 `src/manifest.json` 一致，请求域名校验保持开启。
4. 交付冻结配额的 48 道正式食谱（粥 12、汤 12、菜 16、节庆食品 8）及八个节日节气包，补齐实际来源、版本、审核人和授权/签署记录。`approved` 标记本身不能代替专业审核。
5. 部署符合 `FORMAL_RELEASE_INPUTS.md` 契约的 HTTPS 天气代理，服务凭据只放在服务端；正式模式会启用真实适配器，未配置时回退通用内容并由发布检查阻断。在线、缓存、超时和过期降级逻辑已自动验证，仍须补真实服务与弱网测量证据。
6. 按既有官方资料策略复核来源与平台要求，记录同步失败和人工复核结果。
7. 执行类型检查、M2—M6 工程验证、H5 页面测试、微信构建、`npm run release:check`；真实生产构建成功后才交发布负责人核验。
8. 专业内容、安全、隐私、真实用户和发布负责人共同签署后，由项目所有者决定是否提交审核和发布。

发布检查读取实际食谱文件，而不只检查环境变量是否填写。当前 DEMO 食谱、未审核来源、未达数量配额和未接入真实天气任一条件都会阻断。检查通过也不自动提交、发布或证明签署真实性。

## 发布留档

保留提交 SHA、构建产物、内容库/安全规则版本、发布配置摘要（不含密钥）、测试证据、签署记录、发布时间和批准人。采用独立发布标签标识已批准版本，当前尚未创建正式发布标签。

## 回滚流程

1. 发现安全过滤失效或高风险内容时暂停新发布，停止使用受影响内容，将内容状态设为 `disabled`。
2. 发布负责人选择最近一个已签署、已通过回归的版本；同时核对代码、内容库和安全规则，不把旧代码与新内容混配。
3. 在隔离工作目录或发布流水线中检出该已批准标签并重新验证、构建；保留当前工作目录及用户本机记录，避免通过删除用户数据回滚。
4. 依据实际平台控制台能力，由项目所有者执行恢复并记录操作；未确认权限或平台流程前不自动操作线上发布。
5. 复核受影响收藏的不可用提示、过敏过滤、今日推荐和食材匹配；记录恢复时间和未解决问题。
6. 根因修复后重跑回归与相关人工场景，经同等签署再发布。

当前仅形成方案，尚未进行线上回滚演练，也没有可用于正式回滚的已批准版本。
