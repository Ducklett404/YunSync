## 1. 项目摘要

YunSync（云循）是一套面向体重管理与代谢风险人群的 AI 个体健康行为优化平台。项目不把 AI 定位为“体检报告问答工具”，而是建立一条可以持续学习用户反馈的闭环：

```text
健康数据理解
    -> 风险边界判断
    -> 个体化候选行动生成
    -> 单人随机微实验
    -> 每日低负担记录
    -> 效果与不确定性分析
    -> 下一轮行动调整
```

平台帮助用户回答一个比“什么是健康建议”更具体的问题：

> 在不进行疾病诊断和药物调整的前提下，哪一种低风险生活方式行动对当前的我更容易坚持，并能产生可观察的积极变化？

项目最终将使用华为云完成体检报告 OCR、AI 解释与交互、数据存储、缓存、对象存储、日志监控和容器化部署。开发阶段采用 Mock 服务和合成数据降低早期成本，所有云能力均通过适配层接入，确保本地开发、AI 开发者空间测试和正式云端部署之间可以平滑迁移。

## 2. 立项背景与问题定义

### 2.1 目标问题

现有健康应用通常存在以下不足：

1. 体检报告只能被“解释”，无法转化为可执行、可验证的日常行动。
2. 通用建议没有考虑个人作息、执行成本、身体反馈和既往习惯。
3. 用户同时改变多种习惯后，难以判断哪项改变真正适合自己。
4. 很多应用只展示数据趋势，缺少对照、依从性和干扰因素记录。
5. 大模型直接生成健康建议时，可能出现越界诊断、药物建议或不适当的运动和饮食强度。

### 2.2 项目机会

YunSync 将成熟健康管理项目中的“连续监测、即时反馈、行为教练、习惯养成”机制，与 N-of-1 单人实验和微随机试验思想结合。平台不是替代医生，而是把低风险健康行动变成可追踪的小实验，让用户和指导者看到行动、执行情况和短期反馈之间的关系。

### 2.3 项目定位

- **项目属性**：AI 健康管理与行为优化应用。
- **核心对象**：希望改善体重、活动、饮食和睡眠习惯的成年人。
- **核心能力**：从健康数据到行动建议，再到个人实验和反馈学习。
- **明确边界**：不诊断疾病、不调整药物、不替代专业诊疗、不对高风险人群自动生成自助实验。

## 3. 建设目标

### 3.1 总体目标

在 12 周内完成一套可在华为云稳定运行、可使用合成案例完整演示、具备安全边界和可扩展架构的参赛版本，并形成代码、部署、测试、技术文档、演示视频和答辩材料的完整交付包。

### 3.2 产品目标

1. 用户能在 5 分钟内完成报告上传、指标确认和候选行动选择。
2. 系统能为用户生成一个 14 天、7 个提醒日与 7 个常规日的随机实验计划。
3. 用户每日记录时间控制在 60 秒以内。
4. 平台能针对不同类型行动选择正确的主要观察指标。
5. 结果页面同时展示差异、样本量、完成率、数据缺失和解释限制。
6. 实验结束后，系统能提出保持、调整、延长观察或停止实验等下一步选项。

### 3.3 技术目标

1. 完成前后端分离、分层 MVC、数据库迁移、自动化测试和容器化部署。
2. 接入至少三类华为云能力，其中 AI 能力必须在核心流程中产生可验证作用。
3. 建立本地 Mock、测试环境和正式云环境三套配置。
4. 核心业务接口具备输入校验、审计日志、错误处理和健康检查。
5. 在演示环境中保证核心流程可重复、可降级、可恢复。

### 3.4 参赛目标

1. 形成清晰的真实问题、创新机制、技术实现和社会价值叙事。
2. 用一条合成用户故事在 5 分钟内演示完整健康行动闭环。
3. 提供华为云资源、调用日志、部署拓扑和测试结果作为技术证据。
4. 证明项目不仅能识别和回答，还能根据用户反馈持续调整。

## 4. 目标用户与核心场景

### 4.1 目标用户

| 用户类型 | 主要需求 | 平台价值 |
|---|---|---|
| 体重管理人群 | 找到容易坚持的饮食和活动改变 | 把大目标拆成单一、低负担行动 |
| 代谢风险关注人群 | 理解指标并改善生活方式 | 连接指标、行动和日常反馈 |
| 久坐及睡眠不足人群 | 建立可持续习惯 | 提醒、记录、复盘与个体比较 |
| 健康管理指导者 | 了解用户执行情况 | 查看依从性、趋势和安全事件 |
| 项目研究与运营人员 | 评估产品机制 | 使用匿名统计和审计记录改进产品 |

### 4.2 核心用户旅程

1. 用户阅读知情说明并创建健康档案。
2. 上传脱敏体检报告，或手动录入基础指标。
3. OCR 提取指标，用户逐项确认原文、数值、单位和参考范围。
4. 规则引擎进行适用性与风险筛查。
5. AI 从审核后的行动模板库中排序并解释三个候选行动。
6. 用户选择一个行动，系统生成 14 天随机日程。
7. 用户按日记录完成情况、主要指标和少量干扰因素。
8. 系统计算提醒日与常规日之间的观察性差异。
9. AI 以受控模板解释结果和限制，并生成下一轮建议。
10. 用户选择保持、调整、延长观察或结束实验。

### 4.3 首批行动模板

| 行动 | 提醒日行为 | 常规日行为 | 主要指标 | 安全原则 |
|---|---|---|---|---|
| 饭后轻量活动 | 符合条件的餐后进行自主强度轻量步行 | 保持原有习惯 | 饭后 30 分钟步数、完成率 | 不规定高强度；不适立即停止 |
| 含糖饮料替换 | 原本想喝含糖饮料时选择水或无糖饮品 | 保持原有选择 | 含糖饮料次数、替换完成率 | 不要求用户增加含糖饮料作对照 |
| 进食顺序调整 | 在总食物基本不变时调整进食顺序 | 保持原有顺序 | 餐后状态评分，可选餐后血糖 | 不改变药物和治疗安排 |

## 5. 创新点设计

### 5.1 从“一次回答”升级为“持续学习闭环”

传统报告助手的工作在解释完成后结束。YunSync 把解释结果转化为行动、观察和复盘，使系统能够根据用户自己的执行和反馈进行下一轮调整。

### 5.2 单人随机微实验

项目不让用户连续完成 A、B、C 三组各 7 天的串行实验，而是一次只选择一个行动，在 14 天内随机安排：

- 7 个提醒日：系统提供目标行动提醒；
- 7 个常规日：保持原有生活方式，不主动制造不健康行为；
- 两种条件交错出现，减少时间趋势和周内差异带来的偏差；
- 每轮只验证一个主要问题，避免多项干预同时变化。

该设计兼顾了科学性、执行负担和比赛演示周期。它属于面向产品验证的探索性个人比较，不等同于临床试验，也不用于证明疾病疗效。

### 5.3 安全模板库与 AI 分工

大模型不直接自由生成运动剂量、饮食剂量或药物建议。系统采用以下分工：

- 专业审核模板：定义行动内容、适用条件、禁忌、主要指标和停止条件；
- 规则引擎：执行硬性风险拦截和数据完整性校验；
- 排序算法：根据证据、执行负担、可观测性和用户偏好排序；
- 大模型：负责通俗解释、对话引导和内容个性化，不突破规则边界。

### 5.4 可审计的个体化

实验随机种子、日程、行动版本、数据来源、用户确认和结果解释全部记录。评委可以看到系统为什么推荐、如何随机、如何计算以及何时触发安全拦截。

### 5.5 云端可迁移与离线降级

AI、存储和缓存都使用适配器封装。演示现场即使外部 AI 服务暂时不可用，系统仍可切换到合成数据和规则模板，保证核心流程可演示，同时保留真实华为云调用证据。

| 云端部署 | 数据库、对象存储、日志、监控、容器运行 | 从空环境可重复部署，健康检查正常 |

2. 微信、邮件或应用内提醒，支持提醒时间个性化。
3. 周报、实验对比和个人行动档案。
4. Bootstrap 置信区间或随机置换分析。
5. AI 根据依从性和干扰因素生成下一轮实验草案。
6. 管理端行动模板审核、版本控制和停用机制。
7. 面向指导老师或健康管理者的匿名演示看板。

### 6.3 P2：赛后扩展

1. 多设备连续数据接入。
2. 多行动、多周期和长期自适应策略。
3. 联邦学习或隐私计算研究。
4. 医疗机构合作验证和伦理审查。
5. 多语言、无障碍和区域化健康知识库。

### 6.4 明确不在首个参赛版本中的功能

- 疾病诊断、处方、药物剂量调整；
- 自动制定极端节食或高强度运动计划；
- 用短期个人实验推断长期疾病疗效；
- 无授权采集第三方设备或医疗机构数据；
- 在没有专业审核的情况下开放用户自定义干预剂量。

## 7. 健康学与实验设计方案

### 7.1 设计原则

1. **单一变量**：每轮只改变一个目标行动。
2. **不伤害原则**：常规日不要求用户增加不健康行为。
3. **近端指标**：优先选择在 14 天内可重复观察的行为或状态指标。
4. **随机安排**：由后端生成并锁定提醒日和常规日。
5. **低负担记录**：每天只记录一个主要指标和少量干扰因素。
6. **透明解释**：结果必须同时给出有效天数、缺失情况和局限性。
7. **人工确认**：OCR、健康档案和关键建议都保留用户确认步骤。

### 7.2 单轮实验结构

```text
周期：14 天
提醒日：7 天
常规日：7 天
分配方式：随机且固定
主要结局：每个行动预先定义一个主要指标
辅助指标：完成率、睡眠、主观状态、备注
最小分析条件：提醒日和常规日各至少 2 个有效观测
```

### 7.3 分析方法

第一阶段采用透明、易解释的描述性分析：

```text
观察差异 = 提醒日主要指标均值 - 常规日主要指标均值
完成率 = 已完成行动天数 / 计划总天数
有效率 = 有主要指标记录的天数 / 计划总天数
```

第二阶段增加：

- 中位数和四分位数，降低极端值影响；
- Bootstrap 区间或随机置换检验，展示不确定性；
- 工作日/周末、睡眠、餐食和既往活动的分层描述；
- 敏感性分析：排除明显异常日后重新计算；
- 不进行未经验证的复杂因果推断，不用单一 P 值包装确定性结论。

### 7.4 缺失数据处理

1. 缺失日不自动补零，也不默认视为未完成。
2. 用户可选择忘记记录、设备缺失、身体不适或计划外事件等原因。
3. 主要分析仅使用有有效主要指标的记录。
4. 结果页面同时展示完成率和有效观测数。
5. 缺失比例过高时只提示继续记录，不生成方向性结论。

### 7.5 安全停止条件

出现以下情况时停止自助实验并显示专业帮助提示：

- 胸痛、明显呼吸困难、晕厥或持续眩晕；
- 运动或饮食改变后出现明显不适；
- 用户声明存在医生明确限制；
- 报告或问卷触发预先定义的高风险规则；
- 用户主动选择停止或撤回授权。

所有停止规则需由指导老师或相关专业人员复核，开发团队不得自行扩大医学结论。

## 8. 系统总体架构

### 8.1 逻辑架构

```text
┌──────────────────────────────────────────────────────┐
│ Web / 移动端适配                                      │
│ Vue 3 + TypeScript + Pinia + Router + ECharts         │
└─────────────────────────┬────────────────────────────┘
                          │ HTTPS / REST
┌─────────────────────────▼────────────────────────────┐
│ FastAPI 接口层                                        │
│ 身份验证 | 参数校验 | 限流 | 错误处理 | API 文档       │
├──────────────────────────────────────────────────────┤
│ 业务服务层                                            │
│ 报告解析 | 风险规则 | 行动排序 | 实验计划 | 结果分析     │
├──────────────────────────────────────────────────────┤
│ Repository 与 Integration 适配层                     │
│ SQLAlchemy | OCR | MaaS/大模型 | OBS | Redis          │
└───────────────┬──────────────────────┬───────────────┘
                │                      │
┌───────────────▼──────────┐  ┌────────▼──────────────┐
│ RDS PostgreSQL           │  │ OBS / DCS / AI 服务   │
│ 业务数据、审计与版本      │  │ 文件、缓存、模型调用   │
└──────────────────────────┘  └───────────────────────┘
```

### 8.2 后端分层

| 分层 | 目录 | 职责 |
|---|---|---|
| Controller | `backend/app/controllers/` | HTTP、状态码、输入输出 |
| Service | `backend/app/services/` | 业务流程、安全规则、算法 |
| Repository | `backend/app/repositories/` | 数据查询与持久化 |
| Model | `backend/app/models/` | SQLAlchemy 实体与约束 |
| Schema | `backend/app/schemas/` | Pydantic API 契约 |
| Integration | `backend/app/integrations/` | 华为云及第三方适配器 |
| Core | `backend/app/core/` | 配置、安全常量、公共能力 |
| Database | `backend/app/db/` | 连接、迁移和初始化 |

### 8.3 前端分层

| 分层 | 目录 | 职责 |
|---|---|---|
| View | `frontend/src/views/` | 页面与用户流程 |
| Component | `frontend/src/components/` | 可复用界面组件 |
| Store | `frontend/src/stores/` | 跨页面状态和缓存 |
| Service | `frontend/src/services/` | API 调用和错误转换 |
| Type | `frontend/src/types/` | 前端领域类型 |

### 8.4 关键架构约束

1. Controller 不编写复杂业务计算。
2. 前端不能决定实验分组，分组必须由后端日程确定。
3. AI 输出不能直接写入已确认健康数据。
4. 上传文件与结构化数据分开存储。
5. 所有环境凭据通过环境变量或密钥服务注入。
6. 数据库结构变更必须生成 Alembic 迁移。
7. 外部 AI 服务失败时必须返回明确状态并支持降级。

| 权限与密钥 | IAM、可用密钥管理能力 | 最小权限、凭据隔离和轮换 | P0 |

具体产品名称、区域和配额以比赛账号实际开放资源为准。若开发者空间不适合长期运行，则将其用于开发测试，正式演示服务部署到可持续运行的云主机或容器环境。

### 9.2 云端数据流

```text
用户上传报告
  -> 后端校验类型、大小与授权
  -> 原文件写入 OBS
  -> OCR 提取候选字段
  -> 用户确认结构化指标
  -> 指标写入 RDS
  -> 规则与行动排序服务生成候选项
  -> 大模型生成受控解释
  -> 实验和每日记录写入 RDS
  -> 日志、耗时和错误写入监控系统
```

### 9.3 云服务接入顺序

1. 先接 RDS，验证数据库迁移和连接安全。
2. 再接 OBS，完成上传、读取、删除和权限控制。
3. 接 OCR，保留 Mock 与真实调用对比样例。
4. 接 MaaS/大模型，先使用固定提示词和结构化输出。
5. 接 DCS、日志和监控，不让非核心能力阻塞主流程。
6. 最后完成镜像构建、云端部署、域名和 HTTPS。

## 10. 数据建设计划

### 10.1 数据来源分层

| 数据层 | 来源 | 用途 | 要求 |
|---|---|---|---|
| 合成演示数据 | 团队按数据字典生成 | 开发、自动化测试、答辩演示 | 明确标注“合成”，不得冒充真实用户 |
| 公开研究数据 | 经许可的公开健康或行为数据集 | 验证统计流程和异常场景 | 核查许可、字段定义和使用边界 |
| 团队自测数据 | 成员自愿录入的非敏感行为记录 | 可用性和记录负担测试 | 书面说明、最小采集、可随时删除 |
| 用户授权数据 | 报告、设备、问卷和实验记录 | 未来真实产品验证 | 明示授权、脱敏、访问控制和撤回机制 |
| 系统运行数据 | 审计、错误、性能和模型调用日志 | 质量与运维 | 日志中不得保存报告全文或密钥 |

### 10.2 核心数据实体

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `UserProfile` | 用户 ID、年龄段、目标、风险标记 | 不在演示环境保存真实身份信息 |
| `ConsentRecord` | 授权类型、版本、时间、撤回时间 | 新增，记录数据用途授权 |
| `HealthReport` | 文件引用、来源、状态、创建时间 | 原文件与结构化结果分离 |
| `HealthMetric` | 指标、数值、单位、参考范围、确认状态 | 必须保留来源和确认信息 |
| `ActionTemplate` | 行动、适用条件、安全说明、指标、版本 | 由专业审核后发布 |
| `Experiment` | 用户、行动、周期、种子、日程、状态 | 日程创建后锁定 |
| `Observation` | 日期、分组、完成情况、主要指标、干扰因素 | 分组由后端校验 |
| `AuditLog` | 事件、操作者、对象、时间、摘要 | 支持追踪和答辩证据 |

### 10.3 数据质量规则

1. 指标必须同时包含名称、数值、单位和来源。
2. OCR 结果在用户确认前不能进入推荐计算。
3. 重复记录使用“实验 ID + 日期”唯一约束。
4. 数值设置合理输入范围，但不将范围校验等同于医学判断。
5. 实验分组以服务器保存日程为唯一事实来源。
6. 时间统一保存为带时区时间，用户界面按本地时区展示。
7. 所有模型输出记录模型版本、提示词版本和调用追踪 ID。

### 10.4 隐私与安全策略

- 默认最小化采集，不要求姓名、证件号码和联系方式。
- 演示只使用合成账号、合成报告和合成观测。
- 上传前提示脱敏，服务端限制文件类型和大小。
- 数据传输使用 HTTPS，存储使用访问控制与可用加密能力。
- 开发、测试和生产数据库物理或逻辑隔离。
- 管理员、开发人员和普通用户采用最小权限。
- 用户可查看、导出和申请删除自己的数据。
- 正式试用前由指导老师审查知情说明、风险规则和数据用途。

## 11. AI 与算法开发计划

### 11.1 OCR 结构化流程

1. 文件预检：格式、大小、页数和基本完整性。
2. 图像预处理：方向校正、裁剪、清晰度检查。
3. OCR 调用：获取文字、位置和置信度。
4. 字段抽取：识别指标名称、数值、单位和参考范围。
5. 规范化：统一同义名称和常见单位。
6. 规则校验：检查数值格式、缺失字段和单位冲突。
7. 用户确认：原文与候选结果并排展示。
8. 审计入库：保存确认前后差异，不保存不必要的全文日志。

验收指标：

- 合成标准样例关键字段识别完整率不低于 95%；
- 低置信或单位冲突字段 100% 进入人工确认；
- OCR 失败有明确提示且不产生伪造指标；
- 单份演示报告端到端处理目标小于 15 秒。

### 11.2 候选行动排序

首版使用透明加权模型：

```text
行动适配分 = 证据质量 × 0.40
           + 可观测性 × 0.35
           +（1 - 执行负担）× 0.25
```

完整版本增加用户偏好、既往依从性、时间条件和安全条件，但硬性安全规则始终优先于模型分数。所有权重和模板版本均可追溯。

### 11.3 大模型任务边界

允许：

- 将已确认指标解释为通俗健康管理信息；
- 解释候选行动为什么适合当前目标；
- 将结果改写为易理解的观察性总结；
- 提醒记录、复盘障碍并提出低风险调整选项。

禁止：

- 输出疾病诊断、处方或药物调整；
- 编造未识别到的报告数值；
- 绕过高风险拦截生成实验；
- 把短期行为变化表述为疾病治疗效果；
- 将群体统计直接断言为个人必然结果。

### 11.4 提示词与输出治理

1. 使用系统提示词固定角色、边界和表达口径。
2. 通过 JSON Schema 或结构化协议限制输出字段。
3. 对输出进行关键词、数值和安全规则二次校验。
4. 保存提示词版本、模型版本、延迟和错误码。
5. 建立至少 50 条安全评测样例，包括诱导诊断和药物询问。
6. 高风险或不确定场景使用固定模板，不调用自由生成。

5. SQLite 仅用于本地开发；云端统一使用 PostgreSQL。
6. CI 中从空数据库执行全部迁移并运行集成测试。

| API 集成测试 | 数据库、权限、异常状态、幂等性 | P0 接口覆盖正常和异常路径 |
| 前端组件测试 | 表单、空状态、错误状态、动态字段 | 核心交互可自动验证 |
| 端到端测试 | 上传到结果的完整用户旅程 | 至少 3 条稳定主流程 |
| 安全测试 | 上传、路径、越权、密钥、注入、限流 | 无已知高危问题 |
| 性能测试 | 普通接口、OCR、并发记录、图表加载 | 满足演示指标 |
| 可用性测试 | 完成率、用时、误解和记录负担 | 形成改进记录 |
| AI 评测 | 事实一致性、边界、拒答和结构化输出 | 高风险样例全部拦截 |

### 15.2 必测边界场景

- 空文件、超大文件、错误格式和模糊图片；
- OCR 单位错误、数值缺失和多个参考范围；
- 未确认报告直接请求行动建议；
- 高风险用户直接调用实验接口；
- 前端篡改提醒日/常规日；
- 填写未来日期、周期外日期和重复日期；
- 选择饮料实验却提交步数；
- 数据不足、全缺失、极端值和低完成率；
- Redis、OCR、大模型或 OBS 暂时不可用；
- 页面刷新、移动端、弱网和重复点击提交。

### 15.3 发布门禁

每次进入 `main` 或生成发布版本前必须满足：

```text
后端测试通过
数据库迁移检查通过
前端类型检查通过
前端生产构建通过
敏感信息扫描通过
主流程冒烟测试通过
无未关闭的 P0/P1 缺陷
```

## 23. 项目成功判定

项目成功不以“接入最多云服务”或“生成最多健康建议”为标准，而以下列结果为标准：

1. 用户能够理解并完成一个低风险个人健康实验。
2. 系统能够可靠地区分已确认事实、算法排序和 AI 解释。
3. 实验安排、数据和结果计算可复现、可审计。
4. 平台能够承认数据不足和不确定性，不夸大健康效果。
5. 华为云能力进入核心业务链路，并有真实调用与部署证据。
6. 代码、测试、文档、演示和备用方案构成完整参赛交付。
