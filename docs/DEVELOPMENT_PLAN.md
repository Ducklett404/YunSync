## 1. 修订说明与影响评估

### 1.1 客户需求结论

客户需要的不是以 14 天随机微实验为核心的行为研究平台，而是一套面向普通成年人的体检后食养服务：

```text
上传普通体检报告或手工录入指标
    -> OCR 提取并由用户确认
    -> 识别异常项、变化趋势和风险边界
    -> 补充饮食、过敏、用药与特殊人群信息
    -> 生成药食同源食补方案
    -> 给出材料、用量、替代材料和制作步骤
    -> 用户执行并记录
    -> 按建议周期复查并上传新指标
    -> 对比变化，生成下一版建议
```

### 1.2 修改规模

本次属于重大需求重构，预计影响原计划约 60%—70%。

| 内容 | 处理方式 | 说明 |
|---|---|---|
| 报告上传、OCR、原文对照、人工确认 | 保留并增强 | 仍是系统入口，需要补充单位归一和跨报告映射 |
| 用户授权、隐私、审计、对象存储 | 保留 | 健康数据处理的基础能力不变 |
| 风险规则、AI 输出治理、云架构 | 保留并调整 | 从“实验准入”改为“食养建议准入与转诊提醒” |
| 14 天随机微实验 | 从 P0 移出 | 不再作为产品主流程，仅保留为未来可选研究能力 |
| 行动模板、实验日程、随机分组、组间比较 | 重构 | 替换为食材库、食谱库、组合规则、计划与随访版本 |
| 目标用户、核心旅程、页面和验收指标 | 重写 | 与客户提出的体检—食补—复查闭环对齐 |
| 数据模型、API、测试用例和排期 | 大幅修改 | 增加体检批次、指标趋势、食材禁忌、方案版本和反馈 |

按工作域拆分后的估算如下。百分比表示相对原计划需要新增或改写的比例，不代表当前开发完成度：

| 工作域 | 预计改动比例 | 判断 |
|---|---:|---|
| 产品定位、用户旅程与页面 | 80%—90% | 主线由“微实验”改为“体检—食养—复查” |
| 推荐逻辑与专业内容 | 90%—100% | 需要新建指标目标、食材、食谱、禁忌和审核体系 |
| 报告上传与 OCR | 25%—35% | 基础可复用，新增指标字典、单位归一和跨报告对齐 |
| 数据模型与 API | 50%—65% | 保留账户/报告表，重构实验相关实体与接口 |
| 前端交互 | 60%—75% | 报告确认可复用，方案、采购、反馈、复查页面需新增 |
| 安全、隐私与审计 | 20%—30% | 框架可复用，规则对象和健康内容审计需扩展 |
| 测试与客户验收 | 60%—70% | 验收核心改为建议完整性、安全性和复查闭环 |
| 云部署与运维 | 10%—20% | 部署底座基本保留，补充知识库与模型调用监控 |

综合判断：原计划不能只增加“食谱推荐”页面后继续执行，必须更换产品主流程、领域模型和验收口径；可复用部分主要集中在上传、认证、存储、审计和部署底座。

### 1.3 既有成果处理原则

1. 已完成的认证、授权、上传、OCR 契约、报告确认、审计、云适配器和部署基线继续复用。
2. 旧实验模块不立即删除，先标记为非主流程；待 V2 主流程稳定后再决定归档或迁移。
3. 任何“已完成”状态只代表旧版本工程验收，不自动等同于 V2 客户需求已经完成。
4. V2 的食材内容、禁忌规则、指标映射和推荐模板必须重新验收。

## 2. 项目摘要

YunSync（云循）是一套基于普通体检指标的个体化食养随访系统。用户可上传 PDF、PNG 或 JPEG 体检报告，也可手工录入指标。系统提取并标准化指标，在用户确认后识别异常、临界值和历次变化，结合年龄段、饮食偏好、过敏、疾病史、用药、孕哺状态及肝肾功能等信息，从经过审核的食材与食谱知识库中生成可执行的食补方案。

每条方案必须回答五个问题：

1. 为什么建议这一方案，关联了哪些已确认指标；
2. 需要准备哪些普通食材或目录内食药物质；
3. 每种材料使用多少，有哪些可替代材料；
4. 如何制作、如何安排到一日三餐、建议频次和周期；
5. 哪些人不适合，出现什么情况应停止并咨询医生或营养专业人员。

系统不根据单个指标诊断疾病，不开处方，不调整药物，不使用“治疗、治愈、降到正常”等承诺性表述。系统定位为体检后的膳食辅助与健康随访工具，而不是医疗诊断系统。

## 3. 立项背景与产品定位

### 3.1 用户痛点

1. 普通用户看不懂体检中的缩写、单位、参考区间及多个异常项之间的关系。
2. 报告常只给出“注意饮食、加强锻炼”等笼统建议，难以落实到买什么、吃多少、怎么做。
3. 网络食疗内容来源不明，可能使用非食品原料、夸大功效，或忽略过敏、疾病和药物相互影响。
4. 每次体检报告相互孤立，用户无法直观看到同一指标的长期变化与建议调整原因。
5. 大模型自由生成食谱容易产生不存在的指标、错误剂量、越界诊断或不适合特殊人群的建议。

### 3.2 产品机会

YunSync 将报告结构化、规则安全筛查、可追溯食养知识库、受控 AI 解释和纵向随访整合为一个闭环。产品价值不在“生成更多食谱”，而在于让每个建议都能追溯到已确认指标、用户约束、审核模板和具体制作方法，并在下一次体检后重新计算。

### 3.3 项目定位

- **核心用户**：持有常规体检报告，希望改善日常膳食的成年人。
- **核心场景**：体重、血压、血糖、血脂、尿酸、肝肾功能等常见指标的膳食辅助管理。
- **核心能力**：报告解析、趋势分析、风险分流、食补方案、采购制作、执行反馈和复查迭代。
- **内容范围**：以普通食物为基础，可选用国家现行食药物质目录内原料；优先使用可获得、低负担的家常食材。
- **明确边界**：不诊断、不治疗、不替代医生或注册营养师，不建议停药或改药，不向高风险用户自动提供自助食补方案。

## 4. 建设目标与成功标准

### 4.1 总体目标

完成一套能够演示并逐步投入试用的体检指标食养随访系统，使普通用户在确认报告数据后获得安全、具体、可采购、可制作、可追踪的个体化建议。

### 4.2 产品目标

1. 用户能上传常见体检报告，系统提取指标并展示原文证据、数值、单位、参考区间和置信度。
2. 用户可修改 OCR 结果；未经确认的指标不得进入正式推荐。
3. 系统同时展示本次异常、临界值、历史趋势和需要优先就医咨询的项目。
4. 系统生成 3—5 条优先级明确的膳食建议及 3—7 个可执行食谱，不一次堆叠大量食药物质。
5. 每个食谱包含人数/份量、材料克数、制作步骤、食用频次、替代方案、预计耗时、过敏与禁忌提示。
6. 用户可生成按天或按周的计划和合并采购清单，并记录完成、替换、不适及主观反馈。
7. 用户上传后续报告后，系统能对齐同一指标，展示变化，并说明新方案相对旧方案的保留、调整或停止原因。

### 4.3 技术目标

1. 复用现有前后端分离架构、数据库迁移、自动化测试和容器部署能力。
2. 建立“规则决定安全边界、知识库提供内容、算法完成匹配、AI 负责通俗表达”的推荐链路。
3. 食材、食谱、适用条件、禁忌、来源和版本可审计、可停用、可回滚。
4. OCR、指标归一、规则匹配和方案生成均具备错误处理与降级路径。
5. 健康数据加密存储、最小权限访问，并支持用户撤回授权和删除数据。

### 4.4 V2 成功判定

- 标准合成报告的核心指标抽取完整率不低于 95%；
- 低置信字段和单位冲突 100% 要求用户确认；
- 高风险样例、孕哺/儿童样例、严重肝肾功能异常和已知过敏冲突 100% 被安全规则拦截；
- 所有正式食养建议均能追溯到指标、规则、模板版本与参考来源；
- 所有食谱均包含完整材料和制作步骤，不出现目录外中药材；
- 两次报告上传后，同名指标可正确对齐并生成版本化调整说明；
- 主流程在真实测试者中的任务完成率目标不低于 90%。

## 5. 目标用户、适用范围与核心场景

### 5.1 目标用户

| 用户类型 | 主要需求 | 平台价值 |
|---|---|---|
| 常规体检人群 | 看懂异常和临界指标 | 指标解释、优先级和下一步行动 |
| 代谢风险关注人群 | 改善日常饮食结构 | 量化食谱、替换方案和周计划 |
| 有多次体检记录的人群 | 观察长期变化 | 跨报告指标对齐与趋势说明 |
| 家庭健康管理者 | 为家人准备食材 | 采购清单、制作步骤和禁忌提示 |
| 健康管理师/营养师 | 审核与调整建议 | 方案来源、版本、审核和随访记录 |

首版默认仅服务完成授权的成年人。儿童、孕妇、哺乳期人群、进食障碍、严重营养不良、复杂慢病、肿瘤治疗期、透析及其他需要临床营养干预的人群不进入自动推荐，由系统提示寻求专业指导。

### 5.2 P0 支持的报告与指标

| 指标组 | 示例字段 | 系统用途 |
|---|---|---|
| 基本信息 | 年龄段、性别、身高、体重、BMI、腰围 | 能量与体重管理背景，不单独诊断 |
| 血压 | 收缩压、舒张压 | 风险提示与控盐类膳食原则匹配 |
| 血糖 | 空腹血糖、糖化血红蛋白 | 识别需就医提示或匹配控糖饮食原则 |
| 血脂 | 总胆固醇、甘油三酯、LDL-C、HDL-C | 匹配脂肪结构、全谷物和膳食纤维建议 |
| 尿酸 | 血尿酸 | 匹配饮水、酒精和嘌呤相关膳食提醒 |
| 肝功能 | ALT、AST、GGT 等 | 主要用于安全分流，不宣称食补治疗肝病 |
| 肾功能 | 肌酐、eGFR、尿素等 | 主要用于禁忌与转诊，避免不当高蛋白或高钾建议 |

血常规、甲状腺、肿瘤标志物、影像结论等可被识别和展示，但首版不直接据此自动生成食补方案。系统必须尊重报告自身参考区间，不能用一套固定阈值覆盖所有实验室。

### 5.3 核心用户旅程

1. 用户阅读知情说明，授权健康数据处理并建立档案。
2. 上传 PDF/图片报告，或按模板手工录入指标。
3. 系统 OCR 提取报告日期、机构、项目名、结果、单位、参考范围和异常标记。
4. 用户对照原文逐项确认；系统完成标准名称与单位映射。
5. 用户补充饮食偏好、过敏、忌口、疾病史、用药、孕哺状态、厨具、预算和烹饪时间。
6. 安全规则判断为“可提供一般食养建议”“建议先咨询专业人员”或“需要及时就医”。
7. 系统展示指标摘要和建议优先级，用户确认本周期目标。
8. 系统生成个体化食养方案、食谱卡、周安排和采购清单。
9. 用户记录执行、替换、不适、体重/血压等可选日常数据。
10. 到期提醒用户按体检机构或医生建议复查，而非由系统擅自规定医学复查周期。
11. 用户上传新报告，系统对比趋势并生成新版本方案及变更说明。

### 5.4 主要页面

1. 登录、授权与非诊疗声明页；
2. 健康档案与饮食约束页；
3. 报告上传与处理状态页；
4. 原文—结构化指标逐项确认页；
5. 本次指标摘要与历次趋势页；
6. 风险提示与咨询/就医建议页；
7. 食养目标选择页；
8. 个体方案总览页；
9. 食谱详情页（材料、用量、步骤、替代、禁忌）；
10. 周计划与采购清单页；
11. 执行反馈与不适记录页；
12. 复查上传、前后对比与新方案变更页；
13. 管理端食材、食谱、规则、来源与审核页。

## 6. 产品功能范围与优先级

### 6.1 P0：首版必须完成

| 模块 | 核心功能 | 验收标准 |
|---|---|---|
| 用户与授权 | 登录、知情说明、隐私授权、撤回和删除申请 | 未授权不能上传或分析；授权版本可追溯 |
| 健康档案 | 基本信息、目标、过敏、疾病史、用药、饮食偏好与烹饪条件 | 关键安全字段未完成时不得正式推荐 |
| 报告解析 | PDF/PNG/JPEG 上传、OCR、字段定位、置信度 | 低置信、单位缺失、范围冲突必须确认 |
| 指标标准化 | 别名映射、单位归一、报告批次、同指标历史对齐 | 保留原值和原单位；转换过程可审计 |
| 指标摘要 | 异常/临界项、趋势、数据质量与解释 | 不输出诊断；每条结论能回到原报告 |
| 风险分流 | 高风险、特殊人群、肝肾、过敏和用药提示 | 命中硬规则时阻止自动方案并给出下一步 |
| 食材知识库 | 普通食物与食药物质、来源、部位、属性、禁忌、过敏原 | 仅启用审核通过且当前有效的条目 |
| 食谱模板库 | 材料克数、份量、步骤、频次、替代、营养标签与适用条件 | 每个模板有版本、来源、审核人与状态 |
| 方案生成 | 目标优先级、规则匹配、冲突消解、3—7 个食谱 | 不与过敏/禁忌冲突；解释推荐依据 |
| 周计划与采购 | 7 天安排、份数换算、材料合并、替换与导出 | 采购量可复算；食谱更换后同步更新 |
| 执行反馈 | 已吃/跳过/替换、不适、备注和可选家庭监测 | 不适可触发暂停与安全提示 |
| 复查迭代 | 新报告上传、指标对齐、趋势和方案版本比较 | 显示保留、调整、停止及原因 |
| 管理审核 | 食材、食谱、规则、来源、发布、停用、回滚 | 未审核内容不得进入用户正式方案 |

### 6.2 P1：体验和竞争力增强

1. 体检报告批量上传和多家机构模板适配；
2. 基于家庭人数、预算和地域食材可得性的采购优化；
3. 热量、蛋白质、脂肪、碳水、膳食纤维、钠等估算展示；
4. 微信、短信、邮件或应用内提醒；
5. 用户向营养师发起人工审核，专业人员可批注和锁定方案；
6. 食谱收藏、口味评分、季节替换与厨具筛选；
7. 数据导出、分享给医生或营养师的脱敏报告；
8. 设备或家庭血压计、血糖仪数据导入。

### 6.3 P2：后续扩展

1. 医疗机构或体检中心标准接口；
2. 注册营养师工作台和机构多租户；
3. 在伦理与专业审核下开展真实世界效果研究；
4. 更广泛的慢病食养指南和地区化食谱库；
5. 隐私计算、联邦分析和长期个体化模型。

### 6.4 明确不在首版范围

- 疾病诊断、疗效判断、处方、药物或补充剂剂量调整；
- 根据影像、肿瘤标志物或复杂专科指标自动生成食补方案；
- 中医体质或证候的自动诊断；
- 使用食药物质目录之外的中药材作为普通食材推荐；
- 对儿童、孕哺期、透析、严重肝肾疾病或营养不良人群自动配餐；
- 自动承诺指标改善幅度或替代医学复查。

## 7. 食养方案设计规范

### 7.1 推荐原则

1. **普通食物优先**：先改善整体膳食结构，再考虑少量食药物质点缀。
2. **指标与人共同决策**：单个异常数值不能直接等同于疾病，也不能脱离用户整体情况生成建议。
3. **少而可行**：每周期只突出 1—3 个目标，避免多种原料叠加导致执行困难或风险不明。
4. **有据可查**：每项原则、食材和食谱记录来源、适用范围、版本和审核状态。
5. **安全优先**：规则拦截高于算法排序，人工审核高于 AI 文案。
6. **不夸大功效**：使用“有助于形成合理膳食”“可作为日常选择”等表述，不声称治疗疾病。
7. **动态调整**：后续方案同时考虑新指标、执行反馈、不适和旧方案依从性。

### 7.2 每份方案固定结构

```text
方案版本与生成日期
本期主要目标（最多 3 个）
关联的已确认指标及报告日期
需要优先咨询医生的事项
饮食总原则
每日/每周安排
3—7 张食谱卡
合并采购清单
可替代食材和外食选择
过敏、禁忌、用药与特殊人群提示
执行周期与记录方式
复查依据和上传提醒
参考来源、审核版本和免责声明
```

### 7.3 食谱卡必填字段

| 字段 | 要求 |
|---|---|
| 食谱名称 | 普通、可理解，不使用治疗性名称 |
| 适用目标 | 说明相关膳食原则，不宣称疗效 |
| 份数 | 1 人份/2 人份，可自动换算 |
| 材料 | 名称、可食部克数、食药物质具体部位 |
| 替代材料 | 同类替代及换算，过敏替代单独标识 |
| 前处理 | 清洗、浸泡、去核等必要操作 |
| 制作步骤 | 顺序、时间、火候和所需厨具 |
| 食用建议 | 搭配场景、建议频次、周期和份量 |
| 注意事项 | 过敏、特殊人群、肝肾、用药及不适处理 |
| 来源与版本 | 指南/审核依据、模板版本、审核人和日期 |

### 7.4 食药物质治理

1. 仅收录国家卫生健康行政部门与市场监管部门现行目录或公告允许作为食药物质的品种。
2. 目录变化时由管理员更新状态；已停用条目不能生成新方案，历史方案保留快照。
3. 明确物种、使用部位、炮制/加工形态与食品用途，不能仅按俗名模糊匹配。
4. 对公告提示不推荐的特殊人群、已知过敏、可能的药物相互影响和肝肾风险建立规则。
5. 不将“药典收载”自动等同于“可作为普通食品使用”，目录准入与专业审核缺一不可。
6. 食材库必须由具备营养或中医药相关资质的专业人员审核后发布。

### 7.5 复查与方案迭代规则

- 保留每次报告、确认值和方案快照，不覆盖历史记录。
- 复查时间优先采用体检报告、医生建议或用户既定体检计划；系统只做提醒。
- 对比时同时展示绝对变化、方向、时间间隔、单位和参考范围变化。
- 实验室、检测方法或单位变化时提示可比性限制。
- 单次改善不归因于某个食谱；单次恶化也不自动判定方案无效。
- 数据不足时输出“暂不调整”或“建议专业复核”，不得强行生成新结论。
- 新方案列出变更日志：继续、减少、替换、暂停和新增，并说明依据。

### 7.6 方案生成前置条件与状态

系统不得把“成功调用大模型”等同于“方案可交付”。方案必须经过以下状态流转：

| 状态 | 进入条件 | 用户可见结果 | 允许的下一步 |
|---|---|---|---|
| `DRAFT_UNVERIFIED` | OCR 已完成，但关键指标尚未确认 | 仅显示候选值和原文，不显示正式建议 | 用户确认或修正指标 |
| `NEEDS_PROFILE` | 指标已确认，但关键安全档案缺失 | 显示待补充项 | 补充过敏、用药、疾病与特殊状态 |
| `BLOCKED_REVIEW` | 命中 B/C 层风险或规则冲突无法消解 | 显示咨询/就医提示，不生成自助方案 | 专业审核或补充资料 |
| `READY` | 数据完整、通过硬规则、候选模板充足 | 可预览本期目标和方案草案 | 用户确认方案 |
| `ACTIVE` | 用户确认且最终安全扫描通过 | 展示计划、食谱和采购清单 | 执行、反馈或上传复查数据 |
| `PAUSED` | 新增不适、约束变化或内容被停用 | 方案保留但明确标记暂停 | 重新评估或专业审核 |
| `SUPERSEDED` | 新报告已生成并确认新版本 | 历史只读，可查看变更原因 | 使用最新有效方案 |

以下条件必须全部满足，方案才可以从 `READY` 进入 `ACTIVE`：核心指标已确认；单位与参考范围无未解决冲突；必采安全信息完整；未命中阻断规则；所有材料来自已发布模板；每项材料均通过过敏、疾病、用药和特殊人群校验；输出字段完整；来源与审核版本有效。

### 7.7 客户可见方案示例（仅作格式验收）

下例只用于说明产品应交付到什么颗粒度，不代表针对任何个人的健康建议，也不作为首批正式食谱内容发布。

```text
本期目标：用一份少油、易执行的早餐替换高油高糖早餐
关联数据：用户已确认的体重/BMI及血脂相关指标（显示报告日期和原值）

食谱名称：燕麦山药粥（1 人份）
准备材料：燕麦片 40 g、鲜山药 80 g、水 600 mL
可替代材料：燕麦片可按审核模板替换为等量全谷物；替代后重新计算采购量
前处理：山药去皮切小块；处理鲜山药时建议戴手套，避免皮肤刺激
制作方法：水煮沸后加入山药，小火煮约 15 分钟；加入燕麦片后继续煮至合适稠度
用餐安排：作为早餐的一部分，具体频次由本期计划和个人总膳食安排确定
注意事项：存在相关食物过敏、吞咽问题或医生要求限制相应营养素时不使用
推荐原因：说明其如何匹配本期膳食目标，不使用“治疗、降脂、治愈”等措辞
来源与版本：食谱模板编号、指南来源、审核人、审核日期、内容版本
```

验收重点不是示例食谱本身，而是每个正式方案都必须同时包含“关联指标—材料—用量—做法—频次—替代—禁忌—来源”八类信息。

## 8. 安全、合规与医疗边界

### 8.1 三层安全分流

| 层级 | 系统行为 | 示例 |
|---|---|---|
| A：一般食养 | 可生成方案 | 资料完整、无硬性禁忌、仅需一般膳食改善 |
| B：先咨询再使用 | 暂停自动方案，可保存资料 | 多项明显异常、复杂用药、特殊人群或疑似营养风险 |
| C：及时就医 | 只显示明确就医提示和原报告摘要 | 报告标注危急值、用户报告急性症状或命中紧急规则 |

具体阈值不得由开发人员凭经验编写，必须由临床/营养专业人员依据现行指南、报告参考范围及服务地区要求审核。

### 8.2 必采安全信息

- 年龄段与生理性别；
- 妊娠、备孕、哺乳状态；
- 食物和药材过敏；
- 已确诊疾病与近期手术/治疗；
- 当前处方药、非处方药和补充剂；
- 肝肾功能异常史；
- 吞咽、消化、进食障碍和明显体重异常；
- 医生已明确要求限制的食物或营养素。

### 8.3 输出禁区

系统不得：

- 说用户“患有”某种疾病，除非只是复述用户已确认的医生诊断；
- 建议停药、换药、减量或用食补替代治疗；
- 使用“根治、排毒、逆转、保证改善”等宣传性措辞；
- 推荐来源不明的药材、偏方、超常剂量或长期单一食用；
- 忽略报告原始参考范围或把 OCR 猜测当作事实；
- 在安全资料不完整时生成正式个体化方案。

### 8.4 隐私与数据安全

1. 上传前提示用户遮盖姓名、身份证号、条码等非必要信息，并提供自动脱敏能力。
2. 原文件与结构化数据分开加密存储，使用短时授权访问链接。
3. 日志不记录报告全文、身份信息、密钥或完整模型提示词中的健康数据。
4. 使用最小权限、传输加密、审计日志、备份恢复和数据保留策略。
5. 用户可导出数据、撤回授权并发起删除；删除过程记录状态但不保留健康正文。
6. 真实用户试用前完成隐私政策、用户协议、健康免责声明和专业审核流程。

## 9. 推荐引擎与 AI 分工

### 9.1 推荐流水线

```text
已确认指标 + 历史趋势 + 用户约束
    -> 数据完整性检查
    -> 安全与转诊硬规则
    -> 识别可管理的膳食目标
    -> 检索审核通过的饮食原则和食谱模板
    -> 排除过敏、禁忌、冲突和不可获得材料
    -> 按证据、适配度、可执行性、偏好和成本排序
    -> 生成周计划与采购清单
    -> AI 在固定结构内生成通俗解释
    -> 输出后安全扫描与版本固化
```

### 9.2 规则、算法、AI 与人工职责

| 组件 | 可以做 | 不可以做 |
|---|---|---|
| 规则引擎 | 单位校验、硬性禁忌、安全分流、模板过滤 | 创造医学结论 |
| 匹配算法 | 目标匹配、冲突消解、排序、份量换算 | 绕过禁忌提高推荐分 |
| 大模型 | 报告术语通俗化、方案说明、步骤自然语言组织 | 自创食材、剂量、阈值、来源或诊断 |
| 专业审核者 | 审核食材、食谱、规则和用户特殊方案 | 用个人意见代替必要的医疗诊疗 |

### 9.3 推荐评分建议

候选食谱仅在通过全部硬规则后参与排序：

```text
总分 = 证据与指南匹配度 × 0.30
     + 用户健康目标匹配度 × 0.25
     + 过敏/偏好/地域适配度 × 0.20
     + 可执行性（时间、厨具、成本） × 0.15
     + 食材可得性 × 0.10
```

权重是产品初始值，应通过专业评审与用户测试调整。分数只表示推荐排序，不表示医学疗效概率。

### 9.4 结构化输出约束

大模型输出必须通过 JSON Schema 校验，字段至少包括：`summary`、`linked_metric_ids`、`goals`、`recipes`、`shopping_list`、`contraindications`、`follow_up`、`source_ids` 和 `disclaimer`。任何无法对应到已确认指标、已发布模板或有效来源的内容都应被拒绝或退回重生成。

### 9.5 动态复评决策规则

以下事件触发重新评估，但不一定都生成新食谱：

| 触发事件 | 系统处理 | 方案结果 |
|---|---|---|
| 上传新体检报告 | 对齐同一指标、检查单位/方法/参考范围可比性，再执行完整安全规则 | 生成“继续、调整、暂停或待专业复核”的版本差异 |
| 修改过敏、疾病、用药或医生限制 | 立即重新校验全部材料与模板 | 命中冲突的活动方案自动暂停，不等待下次复查 |
| 记录疑似不适 | 保存发生时间、食用内容和描述，提示停止相关食谱并评估风险 | 相关食谱暂停；严重情形进入就医提示 |
| 依从性低但无新指标 | 优先调整口味、时间、预算、厨具和替代材料 | 不把“没执行”误判为方案无效 |
| 新旧数据不可直接比较 | 展示差异来源和可比性限制 | 可维持原方案或转专业复核，不强行解释趋势 |
| 食材/食谱/规则版本停用 | 对所有引用中的活动方案执行影响分析 | 高风险变更立即暂停，一般变更在下次打开时提示更新 |

方案调整只允许引用版本化规则。具体“变化多少才调整”的阈值由专业审核者配置并记录来源，开发人员和大模型均不得临时推断阈值。

## 10. 系统总体架构

### 10.1 逻辑架构

```text
┌──────────────────────────────────────────────────────┐
│ Web / 移动端适配                                      │
│ 报告确认 | 趋势 | 方案 | 食谱 | 采购 | 随访            │
└─────────────────────────┬────────────────────────────┘
                          │ HTTPS / REST
┌─────────────────────────▼────────────────────────────┐
│ FastAPI 接口层                                        │
│ 身份认证 | 输入校验 | 限流 | 幂等 | 错误处理            │
├──────────────────────────────────────────────────────┤
│ 业务服务层                                            │
│ 报告解析 | 指标归一 | 风险分流 | 方案生成 | 趋势比较     │
├──────────────────────────────────────────────────────┤
│ 知识与规则层                                          │
│ 食材库 | 食谱库 | 指标规则 | 禁忌规则 | 来源与版本       │
├──────────────────────────────────────────────────────┤
│ Repository / Integration                             │
│ PostgreSQL | OCR | 大模型 | OBS | Redis | 通知         │
└──────────────────────────────────────────────────────┘
```

### 10.2 关键架构约束

1. 原始报告、OCR 候选值、用户确认值分别保存，不能相互覆盖。
2. 所有指标转换保留原值、目标值、转换公式和版本。
3. 规则引擎在 AI 之前和之后各执行一次，AI 不能绕过硬规则。
4. 食材与食谱使用发布版本；生成方案保存不可变快照。
5. 前端不得自行判断高风险、改变材料克数或隐藏禁忌。
6. 外部 AI 不可用时，系统可使用规则和审核模板生成基础方案。
7. 无法安全解释的指标只展示原报告与咨询建议，不强制推荐。

### 10.3 华为云能力规划

| 能力 | 计划产品 | 项目作用 | 优先级 |
|---|---|---|---|
| 文档识别 | OCR 服务 | 报告文本、表格与字段候选提取 | P0 |
| 大模型 | 账号实际开放的 MaaS/模型服务 | 受控解释和方案文案 | P0 |
| 数据库 | RDS for PostgreSQL | 用户、指标、知识库、方案与审计 | P0 |
| 对象存储 | OBS | 加密保存报告和导出文件 | P0 |
| 运行环境 | ECS + Docker 或可用容器服务 | 前后端部署 | P0 |
| 权限与密钥 | IAM/密钥管理能力 | 最小权限与凭据管理 | P0 |
| 缓存与任务 | DCS for Redis | 会话、限流和异步处理状态 | P1 |
| 日志监控 | LTS/云监控 | 错误、性能、告警与调用证据 | P1 |

## 11. 数据模型与 API 改造计划

### 11.1 核心数据实体

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `UserProfile` | 年龄段、性别、目标、预算、厨具 | 最小必要信息 |
| `HealthConstraint` | 过敏、疾病史、用药、特殊状态、医生限制 | 推荐硬约束 |
| `ReportBatch` | 报告日期、机构、文件、状态、解析版本 | 一次上传批次 |
| `MetricObservation` | 原文、标准编码、值、单位、参考范围、确认状态 | 单个指标观测 |
| `MetricDefinition` | 标准名、别名、合法单位、换算规则 | 指标字典 |
| `RiskRule` | 条件、等级、提示、来源、版本 | 安全分流规则 |
| `Ingredient` | 名称、物种、部位、类别、过敏原、目录状态 | 普通食物/食药物质 |
| `Contraindication` | 人群、疾病、用药、阈值、处理方式 | 食材和食谱禁忌 |
| `RecipeTemplate` | 材料、克数、份数、步骤、频次、营养估算 | 审核模板 |
| `EvidenceSource` | 标题、发布机构、日期、链接、适用范围 | 来源追溯 |
| `CarePlan` | 目标、周期、状态、来源报告、版本 | 一期食养方案 |
| `PlanRecipeSnapshot` | 方案内食谱、材料、步骤和禁忌快照 | 防止模板变化污染历史 |
| `RecommendationTrace` | 指标、规则、模板、来源、过滤原因、评分 | 解释每条建议为何入选或被排除 |
| `SafetyDecision` | 分流等级、命中规则、输入快照、审核状态 | 固化生成前后的安全判断 |
| `AdherenceLog` | 日期、完成、替换、不适、备注 | 执行反馈 |
| `PlanRevision` | 新旧方案、变更类型、依据 | 复查后的调整记录 |
| `ContentReview` | 内容对象、审核人、结论、有效期、版本 | 支持发布、复审、停用和回滚 |
| `AuditLog` | 操作者、动作、对象、时间、结果 | 合规审计 |

### 11.2 核心 API

```text
POST   /reports                         上传报告
POST   /reports/manual                  手工创建报告批次与指标
GET    /reports/{id}/status             查询解析状态
GET    /reports/{id}/observations       获取 OCR 指标候选
PATCH  /observations/{id}/confirm       确认或修正指标
POST   /reports/{id}/confirm            提交本批次确认结果并锁定输入版本
GET    /metrics/summary                 获取本次摘要与历史趋势
PUT    /profile/constraints             更新过敏、用药和饮食约束
GET    /profile/completeness            查询生成方案前仍缺少的安全信息
POST   /assessments/safety              执行安全分流
POST   /plans/generate                  生成方案草案
POST   /plans/{id}/confirm              用户确认方案
GET    /plans/{id}                      获取完整方案
GET    /plans/{id}/trace                获取指标、规则、模板和来源追踪
GET    /plans/{id}/shopping-list        获取采购清单
POST   /plans/{id}/logs                 提交执行与不适反馈
POST   /follow-ups/compare              比较两次或多次报告
POST   /plans/{id}/revise               根据复查生成新版本
GET    /admin/ingredients               管理食材库
GET    /admin/recipes                   管理食谱模板
POST   /admin/content/{id}/publish      审核发布内容
```

写接口必须支持幂等键；方案生成接口只返回草案，不得跳过用户确认直接进入 `ACTIVE`。当档案不完整、存在未确认指标或命中阻断规则时，接口应返回明确的业务状态和缺失/阻断原因，而不是用通用 500 错误代替。

### 11.3 数据迁移策略

1. 保留现有报告、指标、授权和审计表，新增版本字段和标准指标字典。
2. 将旧 `ActionTemplate` 的可复用饮食内容人工迁移到 `RecipeTemplate`，不得自动发布。
3. 旧 `Experiment`、随机日程和组间分析接口标记为 deprecated，不出现在 V2 默认导航。
4. 创建数据迁移脚本和回滚脚本；迁移前完成备份并在副本数据库演练。
5. 历史合成数据继续标注为合成，不转换成真实用户案例。

## 13. 测试与验收计划

### 13.1 测试分层

| 测试类型 | 重点内容 | 目标 |
|---|---|---|
| 单元测试 | 单位换算、规则、冲突消解、份量与采购换算 | 核心服务覆盖率不低于 80% |
| API 集成 | 权限、幂等、状态机、数据库和外部适配器 | P0 正常与异常路径覆盖 |
| OCR 回归 | 多机构版式、模糊图片、表格、单位和参考范围 | 标准集核心字段完整率 ≥95% |
| 推荐金标准 | 指标—目标—模板匹配、禁忌和排序 | 由专业人员标注并逐版本回归 |
| AI 安全评测 | 幻觉、诊断、调药、目录外材料、承诺疗效 | 高风险诱导拦截率 100% |
| 端到端测试 | 两次报告、方案、采购、反馈和更新 | 至少 3 条稳定主流程 |
| 可用性测试 | 完成率、耗时、理解度和烹饪可执行性 | 真实记录并形成整改清单 |
| 安全测试 | 越权、文件、隐私、密钥、日志和删除 | 无已知高危问题 |

### 13.2 必测边界场景

- 报告模糊、旋转、重复页、多个日期、多个参考范围；
- 同一指标不同单位、实验室和检测方法；
- OCR 把小数点、正负号或上下标识别错误；
- 用户未确认指标就请求方案；
- 用户未填写过敏、用药或孕哺状态；
- 报告标注危急值或用户报告急性不适；
- 食谱同时命中过敏、疾病、用药或医生限制；
- 推荐材料不在有效目录、部位不一致或模板已停用；
- 多个指标的膳食方向发生冲突；
- 采购换算后出现零值、负数、异常大份量或单位混乱；
- 新旧报告单位或参考范围变化导致趋势不可直接比较；
- AI 尝试增加模板外食材、修改克数或生成治疗承诺；
- OCR、模型、OBS、Redis 或数据库暂时不可用；
- 用户撤回授权、删除报告或要求导出全部数据。

### 13.3 客户验收用例

1. 上传一份含血压、血糖、血脂、尿酸、肝肾功能的普通体检报告。
2. 用户能在原文旁确认或修正每个关键指标。
3. 系统指出需优先咨询的项目，并清楚区分提示与诊断。
4. 用户补充过敏、忌口、预算和烹饪时间后生成方案。
5. 方案至少包含材料克数、步骤、频次、替代、采购清单和禁忌。
6. 修改过敏或用药信息后，冲突食谱立即失效并重新评估。
7. 上传第二份报告后，系统正确对齐指标并展示变化与可比性限制。
8. 新方案明确列出相对旧方案的调整及原因。
9. 管理员能查看每项建议使用的指标、规则、模板和来源版本。
10. 外部模型不可用时，系统仍可提供审核模板生成的基础方案或明确降级提示。

| 后端与云开发 | API、数据、规则、云接入和部署 | 迁移、接口、部署与审计证据 |
| 前端开发 | 报告确认、趋势、方案、食谱和随访体验 | 可用页面与交互测试 |

## 16. 主要风险与应对

| 风险 | 概率 | 影响 | 应对措施 |
|---|---|---|---|
| 食补建议被理解为治疗 | 高 | 高 | 非诊疗声明、措辞白名单、界面分流、专业审核 |
| OCR 数值或单位错误 | 高 | 高 | 原文定位、置信度、人工确认、转换审计 |
| 目录或指南更新 | 中 | 高 | 来源版本、定期复核、停用和历史快照 |
| 食药物质与用药/疾病冲突 | 中 | 高 | 必采安全档案、硬规则、人工复核和保守拒绝 |
| 多项指标建议相互冲突 | 中 | 高 | 目标优先级、冲突矩阵、减少目标、转人工 |
| AI 编造食材、剂量或功效 | 中 | 高 | 受控检索、Schema、模板白名单、输出后扫描 |
| 真实效果被过度归因 | 高 | 中 | 只做趋势描述，不宣称因果或疗效 |
| 用户无法采购或制作 | 中 | 中 | 替代材料、预算/地域/厨具筛选和可用性测试 |
| 健康数据泄露 | 低 | 高 | 最小采集、加密、脱敏、权限、审计和删除 |
| 旧实验代码增加维护成本 | 中 | 中 | 隐藏旧入口、接口弃用、分阶段迁移与归档 |
| 缺少专业审核人员 | 中 | 高 | 作为发布阻断项，不以 AI 审核代替专业签字 |

## 17. 当前基础、差距与立即行动

### 17.1 可直接复用的基础

- 受控 AI 输出、规则模板和测试基础设施。

### 17.2 V2 尚未完成的关键能力

- [ ] 客户确认的新需求规格和页面原型；
- [ ] P0 指标字典、单位换算和跨报告趋势；
- [ ] 完整过敏、用药、疾病和特殊人群档案；
- [ ] 经专业审核的食药物质与普通食物知识库；
- [ ] 含材料克数、制作步骤、替代和禁忌的食谱库；
- [ ] 从指标到食谱的规则、冲突消解和排序；
- [ ] 周计划、采购清单和执行反馈；
- [ ] 复查报告对比、方案版本和变更说明；
- [ ] V2 专业内容审核、真实用户测试和客户验收；
- [ ] 真实华为云联调、部署与监控证据。

### 17.3 启动前必须由客户确认的问题

1. 首版服务地区及适用的监管和食药物质目录；
2. 首版只服务成年人，还是必须覆盖儿童、孕妇或老年特殊人群；
3. 首批必须支持的体检指标和报告样例；
4. 建议是一周菜单、单个食谱，还是两者都要；
5. 是否需要热量和营养素精确计算；
6. 客户能否提供临床营养或中医药专业审核人员；
7. 是否需要营养师人工服务、商城采购或付费功能；
8. 数据部署地区、保存期限和删除要求。

在上述问题未确认前，可以建设通用底座和合成数据原型，但不能宣称正式健康内容已经验收。

### 17.4 客户确认后的首个五个工作日

| 时间 | 必须完成的动作 | 输出 |
|---|---|---|
| 第 1 日 | 与客户逐条确认 CR-01—CR-10、P0 指标和排除人群 | 签字版需求基线与未决项清单 |
| 第 2 日 | 收集 10—20 份脱敏/合成代表性报告并登记版式 | 报告样本清单与字段覆盖矩阵 |
| 第 3 日 | 完成“上传—确认—方案—食谱—复查”关键页面原型 | 可点击原型与页面验收意见 |
| 第 4 日 | 专业人员审核首批指标目标、阻断规则和食谱字段模板 | 内容审核记录与待补证据项 |
| 第 5 日 | 以一名合成用户走通两次报告和方案变更 | 端到端演示、缺口清单和更新后排期 |

五日检查点的通过条件是客户能从原型中清楚看到：上传什么、系统如何确认、建议为何产生、需要买什么、如何制作、何时停止、下次上传后会发生什么。若其中任一问题无法回答，不进入大规模编码。

## 21. 政策与专业依据

本计划的产品边界和内容治理以正式发布时有效的法律法规、国家目录、卫生健康部门食养指南和专业审核意见为准，并建立定期复核机制。首批重点依据包括：

1. 国家卫生健康委员会：[《按照传统既是食品又是中药材的物质目录管理规定》](https://www.nhc.gov.cn/sps/c100088/202111/a0f07a6f1d4f4607add51e5a9de73abe.shtml)及后续目录、增补公告；
2. 国家卫生健康委员会、国家市场监督管理总局：[《关于党参等 9 种新增按照传统既是食品又是中药材的物质公告》](https://www.nhc.gov.cn/sps/c100088/202311/5b062dd13fe646198b56c7d76a99aab4.shtml)、[《关于地黄等 4 种按照传统既是食品又是中药材的物质的公告》](https://www.nhc.gov.cn/sps/c100088/202408/53150d0918ec40899b5293147ec0dd01.shtml)等动态增补文件；
3. 国家卫生健康委办公厅：[《成人高脂血症食养指南（2023 年版）》等 4 项食养指南](https://www.nhc.gov.cn/sps/c100088/202301/f01895a06c5349ef999f25da833c166d.shtml)；
4. 国家卫生健康委办公厅：《成人高血压食养指南（2023 年版）》与《成人糖尿病食养指南（2023 年版）》（均见上述 2023 年通知及附件）；
5. 国家卫生健康委办公厅：[《成人高尿酸血症与痛风食养指南（2024 年版）》等 4 项食养指南](https://www.nhc.gov.cn/sps/c100088/202402/9ba512ba8e314a47a181db11d2fa188d.shtml)，其中还包括成人肥胖和成人慢性肾脏病食养指南；
6. 国家卫生健康委员会 2025 年公开答复中关于[已公布纳入食药物质目录的物质为 106 种](https://www.nhc.gov.cn/wjw/jiany/202508/6141c788fa794723afb4e71af48b3d93.shtml)的说明；该数量只作为核查线索，系统不得硬编码，应以正式上线时有效目录为准；
7. 《中国居民膳食指南（2022）》及后续有效版本；
8. 国家卫生健康委员会：[《健康体检管理暂行规定》](https://www.nhc.gov.cn/wjw/gfxwj/200908/c01150ac71544b95ac004b1e8b937182.shtml)，以及国家关于食品安全、个人信息和数据安全的现行规定。

这些资料用于建立一般膳食原则、内容准入和安全边界，不代表系统具备临床诊断或治疗资质。以上链接于 2026 年 9 月 18 日核查；真实上线和每次内容库发布前，仍应由服务地区的法律、隐私、营养和中医药专业人员复核其有效性。

## 附录 A：旧版工程里程碑与 V2 迁移关系

本附录用于兼容仓库既有验证报告和自动化文档检查，不代表旧版“随机微实验”仍是 V2 产品主流程。旧里程碑中已经通过本地测试的工程能力可作为迁移输入，但当前不伪造完成：未经真实云环境、真实用户或专业人员验证的事项仍保持未完成。

| 旧版里程碑 | 可复用工程资产 | V2 处理方式与完成边界 |
|---|---|---|
| 里程碑 M3A | 身份、授权、健康档案和审计基础 | 扩展过敏、用药、疾病与特殊人群字段；旧验证不等同于 V2 健康档案验收 |
| 里程碑 M4A | 报告上传、OCR 契约、失败恢复和指标校对 | 迁移到报告批次、单位归一和跨报告对齐；真实 OBS 与真实 OCR 接入仍保持未完成 |
| 里程碑 M5A | 模板治理、版本和受控解释基础 | 旧行动模板只作为人工迁移候选；专业审核和真实 MaaS 接入仍保持未完成 |
| 里程碑 M6A | 状态机、幂等和日程锁定经验 | 不继续扩展随机实验，改用于 `CarePlan` 状态和版本控制 |
